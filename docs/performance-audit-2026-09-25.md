# onFlows: производителност и архитектура, 25.09.2026

Обхват: Next.js навигация и сървърни четения, FastAPI, Supabase заявки и
права, приемане на Intervals събития, работник, жизнен цикъл на плановете,
научни модули, тестове и staging инфраструктура. Начална версия:
`c542da0ea261ba134ef7bd1868e9735c6f87e367`.

## Доказани причини и корекции

| Причина | Корекция | Запазено поведение |
| --- | --- | --- |
| Календарът групира по целия голям snapshot и разопакова пълни HRmod JSON резултати за няколко малки полета. | Еднократно агрегиране на активностите; отделна компактна таблица с точни JSON проекции. | Същите активна генерация, ревизия, дати, подредба, полета и изолация между профилите. |
| Журналът изтегля десет пълни плана, за да покаже статус и причини. | PostgREST избира само полетата на журнала. | Пълните неизменяеми ревизии остават съхранени. |
| Нова HTTP връзка/клиент за всяка API заявка, без общ жизнен цикъл. | Един ограничен HTTP pool на процес, затварян при спиране. | Ключовете остават в repository; няма глобален кеш на потребителски данни. |
| Седмичният екран прави четири API четения с повтарящи се входове. | Един endpoint за страницата и изрично ограничен кеш само за текущото четене. | Същите услуги и резултати; записите и проверките за конфликт не използват кеша. |
| Синхронни DB/HTTP операции в асинхронния webhook блокират event loop. | Изпълнение в thread pool и тест с блокираща фиктивна база. | Отговорът идва след трайното enqueue; идемпотентност и грешки са запазени. |
| Излишни health проверки и застъпващо се периодично опресняване. | 30 секунди кеш само за успешен health; инвалидиране при инфраструктурна грешка; следващо опресняване след завършване на предишното, с abort при напускане. | Текущите модели и права не се кешират между заявки. |
| Менюто изглежда блокирало, докато чака сървърната страница. | Видим статус за навигацията чрез React transition. | Запаметени филтри и нормалното поведение на връзките се запазват. |

Повтарящият се код за management четенията е заменен с общия API клиент.
Добавени са структурирани времена, брой DB заявки и обем на отговорите без
профилни идентификатори, токени, query параметри или съдържание.

Само премахването на GROUP BY по snapshot даваше 3150,212 ms; оставащото
разопаковане на големите JSON документи обосновава отделните проекции.
Компактната таблица заема 2 908 160 bytes с индексите; оригиналната таблица
остава канонична и не е пренаписана или изтрита.

413 MB от 512 MB и CPU близо до лимита. Няма достатъчен еднакъв товар за
коректно твърдение за процентно намаление на CPU/паметта.

## Проверки

- Начална регресия: 1203 Python + 254 web теста.
- Пълно JSON равенство на стария и новия календар в една DB снимка: 129
  активности, втори профил, празен период, един ден и липсващ профил.
- Всичките 1375 проекции съвпадат с оригиналите, включително null стойности,
  input key, configuration fingerprint и created_at.
- Седмичен и дългосрочен management отговор: равенство с отделните услуги;
  изолация по заявка/профил, независими копия, отказ за кеширане на записи.
- Webhook: health отговаря, докато DB операцията още чака; enqueue завършва
  преди успешния webhook отговор.
- TypeScript, lint и production build преминават.

Няма промени в `biathlon/`, `hrmod_lab/`, `vflat_b65/` или научните engine
файлове. Генерирането, възстановяването, прогресията, скоростните модели,
CAS ревизиите, worker lease/fencing и правилата за активиране са запазени.

## Архитектура и растеж

Разделянето на web, API и фонов работник е правилно. PostgreSQL опашката вече
има lease, fencing, идемпотентност и `SKIP LOCKED`; не е необходим нов брокер,
за да се поправят установените забавяния. Новите read проекции отделят
интерактивните четения от тежките научни резултати.

Текущият staging използва безплатни API/web инстанции и един работник. Тези
измервания **не доказват капацитет за десетки хиляди едновременни потребители**.
Преди такъв етап остават конкретни задачи:

1. Платени постоянно работещи инстанции и тестове с представителен микс от
   четения, синхронизации и генериране на планове; цели за p95/p99, грешки,
   памет и възраст на опашката. Нужен е брой едновременни сесии, не само
   регистрирани акаунти. Планове и брой инстанции не са променяни тук.
2. Измерено увеличаване на работниците; due-plan проверката използва общ
   периодичен обход и CAS. Преди голям брой работници трябва отделно заявяване
   на due планове, за да не се пресмята един и същ план паралелно.
3. Глобално пакетно почистване и за неактивни профили. Сегашният retention се
   задейства при синхронизация и не покрива всички напуснали потребители.
4. Ограничени заявки/страници за големи организации и акаунтни списъци;
   сегашните account четения разчитат на RLS, но могат да връщат много видими
   записи. Правата не бива да се ускоряват с глобален потребителски кеш.
5. Постепенно разделяне на големите `main.py` и `oauth_store.py` по
   отговорности с проверки на API договорите. Масово местене на файлове няма
   доказан ефект върху текущото забавяне.

Не са изтрити научни резултати, история или лабораторни/съвместими модули без
доказателство, че са неизползвани. Премахната е доказаната излишна работа.

## Миграция, достъп и връщане

`20260925061426_performance_read_projections.sql` е приложена само в staging.
Таблицата има RLS и няма SELECT права за `anon`/`authenticated`; service_role
има необходимите права. Trigger поддържа проекциите в същата транзакция;
FK cascade ги премахва при retention на оригинала.

Security advisor отбелязва RLS без политики — това е умишленият достъп само
през сървъра, проверен с реални grants. Другите съществуващи бележки са за
двата RPC за организации и password protection, не са причинени от промяната.
Виж [RLS проверката](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy),
[SECURITY DEFINER проверката](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable)
и [защитата на пароли](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).

Редът за rollout е DB → API/worker → web. Старият код е съвместим с добавената
таблица и новия договор на календара. При проблем може да се върнат трите
услуги към началния commit, като добавената таблица остане. Не се връщат
потребителски данни или научни резултати. Production не е променян.

Повторяемият SQL тест е в `scripts/benchmark_read_projections.sql`; старият
и новият вариант се изпълняват върху един и същ актуален набор от данни.
